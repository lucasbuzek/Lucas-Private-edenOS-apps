## Product mapping: mythology as functional semantics
- BIFROST: the complete product. The Bifröst metaphor names the interconnection system. BIFROSTcore (the runtime) owns CONNECT · KEEP · RESOLVE across properly authorized local/remote transports; it does not erase independently usable specialist apps.
- HEIMDALL: guide/wayfinder and user-facing workspace/configuration function. It helps discover characters, appropriate destinations, journeys, required consent and status. Existing HEIMDALL Organize & Understand retains its original domain state and authority; the full BIFROST App remains primary systems-management UI.
- CHARACTERS: existing EDEN specialist Apps, in-chat identities and ChatGPT plugins such as PENELOPE/JANITOR/SKALD, each owning its domain and actual approved capabilities; naming/persona/role alone NEVER grants execution.
- DESTINATIONS: typed runtime targets, accounts, devices, repositories, servers, tools, signed-in provider contexts and deployment environments. Identity/authorization/location/health must be resolved, not inferred.
- JOURNEYS: bounded tasks/deployments through verified paths, with source→action→destination identity, explicit grant, execution owner, response, receipt, failure/retry/recovery and postcondition verification.
- APPLE VOICE: configurable presentation/persona for spoken results; distinct from the APPLE engineering specialist and from the OS-owned Siri assistant.
- Siri / HEIMDALL / BIFROST: alias-like INVOCATIONS to the same stable typed action IDs through actually supported App Intents / Shortcuts / ChatGPT / native surfaces. They do not alter the operating-system Siri wake phrase and do not create rival schedulers.
- Marvel's depiction is a conceptual reference only; use distinct original EDEN visual identity, assets, naming and descriptions; no claim of affiliation or licensed Marvel imagery.

## Account enrollment and account creation: safe hybrid WebKit + official auth
The current BIFROST `Sources/BifrostLocalDashboardWebView.swift` is STRICTLY nonpersistent and loopback-only, deliberately disallowing external login and browser automation. Retain those protections; do NOT turn that view into an unrestricted signup browser.
Introduce a *separate* Account Journey module using each provider's supported API/official website:
A. User specifies provider, purpose, personal/business/family identity partition, intended email/account label and desired access/capabilities. Do not expose unrelated user data in discovery.
B. Resolve a verified provider-specific manifest: official allowlisted origins, enrollment link, authentication method, capability scopes, account creation provisionable-via-official-API flag, callbacks, login/logout/revoke and credential owner. Unknown origin/provider → unsupported; no arbitrary form automation.
C. HEIMDALL/BIFROST App previews the provider, official destination, data/scope leaving the device, ongoing cost (if any), human involvement, and approval needed. First-use Allow Once / Allow All / Deny applies only to the named BIFROST *capability*, never to vendor or OS consent. Onboarding and paid/costly actions require separate explicit acceptance.
D. When the provider supports native OAuth, use `ASWebAuthenticationSession` and proper registered callback, state validation and PKCE. On macOS this may invoke the configured system browser, which must be checked against current AppDev browser restrictions (Google Chrome is forbidden for EDEN agents). Use approved non-Chrome browser paths, such as official Safari, for manual guided registration where needed. Do not make an embedded WKWebView process a third-party OAuth login.
E. For account registration, automate permitted preparation/provider API operations only after informed user approval. User completes human challenges: unique username/identity proof, password/passkey, captcha, TOS, MFA, email/phone verification, payments. NO generic credential scraping, headless bot signups, CAPTCHA bypass, password extraction, fabricated legal identity or unapproved purchase/consent.
F. On success, verify the exact provider/account identity by supported callback/provider API. Store tokens with correct provider/Keychain/private credential owner; BIFROST holds minimum references and scoped grants, never duplicated plaintext secrets or copied browser cookies. Personal, Business, spouse/family and different user identities cannot be silently merged or shared.
G. Provide distinguishable states: DISCOVERED → SUPPORTED → PREPARED → HUMAN_ACTION_REQUIRED → AUTHENTICATING → VERIFICATION_REQUIRED → CONNECTED_VERIFIED or FAILED / UNKNOWN / REVOKED. Site opened != account created; OAuth callback != service-ready until capability verification. Multiple accounts remain independently selectable and revocable; never auto-switch accounts to evade provider quotas.
H. Enable user-initiated review, reauthorization, disconnect, revoke, recovery and receipt inspection. Provide a human-readable receipt identifying source, provider, account alias, requested scopes, authorization evidence, verified provider identity, timestamp and unresolved requirements; NEVER log secrets.
