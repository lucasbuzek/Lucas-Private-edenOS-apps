====================================================================== 1.
CANONICAL IDENTITY
======================================================================

PROJECT: BIFROST SYSTEM: edenOS / EDEN AppDev

Canonical identity: CONNECT · KEEP · RESOLVE

BIFROST is system-level connective infrastructure, Base App/gateway,
App/service manager, capability/provider resolver, persistent connective
fabric, and user-facing access/control surface.

BIFROST has three primary product jobs:

1)  CONNECT Connect authorized devices, machines, EDEN Apps, services,
    providers and representations. Discover presence/capability,
    establish trust, maintain/recover connections, and resolve where/how
    a capability can execute.

2)  SET UP / INSTALL / MANAGE Discover existing Apps/services/tools;
    import/install/update/repair/rollback modular packages; manage
    compatible headless services, provider connections and shared-host
    relationships; offer useful missing components without needless
    duplication.

3)  PRESENT / CONTROL Expose BIFROST-owned/managed functions through
    synchronized representations including headless/API, menu bar,
    native desktop UI, Web/WebApp/PWA and authorized remote
    control/management.

Historic phrase: “My Gateway to EDEN.” Lucas Private/Custom front door:
Garden of EDEN. Garden of EDEN is a Private configuration/name, not the
universal BIFROST product name.

======================================================================
2. RESPONSIBILITY BOUNDARIES
======================================================================

BIFROST = CONNECT · KEEP · RESOLVE. It owns connective
identity/state/metadata, representations/locations,
relationships/provenance, devices, capability/provider discovery and
resolution, connection state, interoperability, relevant
install/package/update relationships, generic shared-host
infrastructure, and presentation/access to managed BIFROST functions.

HEIMDALL = ORGANIZE & UNDERSTAND. HEIMDALL owns Workspaces, composition,
user working environments, adaptive/custom compositions, contextual
presentation, panels, inspectors and contextual actions. BIFROST MUST
NOT recreate HEIMDALL’s Workspace engine.

SPECIALIST APPS = SPECIALIZE & DO. Specialist Apps retain domain
authority, domain logic, data, APIs/capabilities, representations and
standalone implementation.

CONDUCTOR = reasoning/orchestration/co-ordination. BIFROST is not the AI
assistant. AI reasons; deterministic/native/specialist services execute.

FORGE/ForgeMASTER and the established AppDev production/governance
system remain separate from BIFROST runtime responsibilities.

LCAS FULL remains a persistent in-chat UI/status presentation layer
only, not a BIFROST runtime dependency, governor or orchestrator.

Core rule: HOSTING IS TRANSFERABLE; OWNERSHIP IS NOT.

======================================================================
3. CAPABILITY MODEL
======================================================================

Keep these concepts distinct:

TYPE ≠ CAPABILITY ≠ PROVIDER ≠ INSTANCE / CONNECTION ≠ REPRESENTATION ≠
WORKSPACE / COMPOSITION

BIFROST discovers/registers/resolves authorized capabilities and
representations. It does not swallow specialist App databases or domain
ownership.

Canonical capability-first execution principle:

RECOVER → DISCOVER → RECOGNIZE → REUSE → RECONCILE → INTEGRATE / ADAPT →
BUILD ONLY THE GAP → VERIFY

Related rule: IMPLEMENT / INTEGRATE EXISTING CAPABILITY BEFORE
RECREATING IT.

Native First does NOT mean native at all costs. Use the lowest
sufficient capability/representation.

Canonical representation progression:

LINK → WEB / TAB → EMBED → NATIVE BRIDGE → NATIVE

Stop at the lowest representation that provides the required experience,
reliability, privacy, offline capability, safety, performance and
integration.

7. SHARED HOSTING
======================================================================

Apps remain genuinely standalone.

hosting to BIFROST:

standalone authority or data.

BIFROST may provide shared runtime/service infrastructure without
becoming the specialist domain owner.

======================================================================

Current Native Bridge research adds a richer representation to the

BIFROST REMOTE APP SURFACE

Purpose: Allow a remote/mobile device to interact with an individual
App/workflow without streaming or reproducing the entire desktop.

architecture.

15. LOCAL — NATIVE / LOCAL-FIRST BIFROST
======================================================================

LOCAL is the native BIFROST foundation.

Primary Apple-priority architecture: - local IPC/XPC/Unix-domain socket
where suitable - localhost service/MCP where suitable - MCP stdio for

underlying capability itself is local/offline.

Potential route order: same process/device local → local IPC/localhost →
direct LAN → optional remote transport

======================================================================
16. ALPHA — CLOUDFLARE-ASSISTED BIFROST
======================================================================

ALPHA extends LOCAL beyond the LAN using Cloudflare where useful.

Cloudflare is NOT BIFROST and NOT an AI provider. It is an optional
multi-capability infrastructure/provider adapter.

Potential uses: - remote ingress/tunnel - TLS/edge -
authentication/access - Web/PWA deployment - DNS - edge/API functions -
other suitable Cloudflare services

BIFROST capabilities remain owned by BIFROST/specialist Apps. Cloudflare
is a replaceable implementation/provider for relevant infrastructure
capabilities.

ALPHA also uses Cloudflare deployment to make BIFROST Web / Garden of
EDEN / authorized Remote App Surfaces accessible from mobile and other
browsers where appropriate.

Potential clients: - iPhone/iPad - Android phones/tablets -
Mac/Windows/Linux browsers - other lightweight devices

The Web/PWA surface should be responsive and capability-driven, not a
desktop screenshot.
