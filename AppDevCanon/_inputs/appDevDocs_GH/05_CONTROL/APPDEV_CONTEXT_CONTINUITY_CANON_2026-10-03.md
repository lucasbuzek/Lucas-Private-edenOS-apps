# APPDEV CONTEXT CONTINUITY / ANTI-HALLUCINATION CANON
Updated: 2026-10-03

## Core rule
Context loss must cause retrieval, never reconstruction.

If an agent loses track of project canon, active goal, accepted design, LKG, current candidate, known failures, protected behavior, required platforms/providers, or evidence state, it must re-read durable authority before acting.

UNKNOWN must cause lookup or remain UNKNOWN.
UNKNOWN must never be filled by invention.
Immediate bug-fix context does not supersede the Project Bible.
Local success does not override project invariants.

## Required retrieval order
1. repository/root identity
2. global AppDev authority
3. project Bible
4. project AGENTS/HANDOFF
5. current Git/worktree and source
6. LKG/current candidate evidence
7. affected asset/reference/specification

## Active contract
Every coding/repair session must load a concise active contract before implementation containing:
- project/product
- current milestone
- authoritative baseline/LKG
- current candidate
- hard invariants
- protected capabilities
- required platforms/providers/characters
- prohibited regressions/fallbacks
- acceptance gates
- exact next executable action

The contract is rechecked after each meaningful increment. A repair that breaks an invariant is a regression even if it compiles.

## Evidence
GENERATED != IMPLEMENTED != BUILT != TESTED != VERIFIED != RELEASED.
UNKNOWN != PASS.
Commands are authorization, not evidence.
Build numbers, commits, blobs, plans and status text are not product progress.

## Execution
AUTO means continue safe available work until milestone or genuine unavailable dependency.
FAILED/UNVERIFIED/PIPELINE INCOMPLETE are not blockers when safe repair work remains.
A retry must change something relevant.
